# Кампус — мини-приложение для мессенджера MAX

**Кампус — первокурснику: справка файлом в чат, ответы по регламентам, свои люди.**

Справки и заявления без визита в деканат — готовый PDF приходит прямо в чат MAX.
Ассистент отвечает по регламентам вуза. Афиша событий, конкурсов и хакатонов —
навигация на старте учёбы и карьеры, а «Люди» — безопасная среда для знакомств:
только подтверждённые студенты вуза, контакт открывается при взаимном отклике.

**Хакатон по разработке чат-ботов и мини-приложений для MAX.**
Направление — образовательные решения. Бот: **@t355_hakaton_max_bot**

> **Тезис продукта.** Это не сайт в обёртке мессенджера. Это двусторонний канал:
> заявка уходит из приложения, а готовая справка возвращается **файлом прямо в чат**.
> Почта заменяется не формой, а замкнутым циклом с видимым статусом.

Регистрироваться и вводить коды не нужно: каждый аккаунт получает свою копию

### В MAX — главный путь: справка файлом в чат

1. Открыть бота и нажать «Начать» — придёт приветствие с тремя шагами и кнопкой
   **«Открыть приложение»**.
2. Кнопка → **«Попробовать как студент (демо)»** — демо-профиль с вашим именем из MAX:
   1 курс ИМИТ, группа Б-25-1, зачётка `DEMO-…`.
3. На главной, в карточке «Справка — файлом в чат» → **«Справка об обучении»**.
4. Выбрать, куда нужна справка → **«Получить PDF сразу»**. Шаги заявки проходят за
   пару секунд, через несколько секунд в чат с ботом приходит «заявка принята»
   с кнопкой «Открыть заявку», а следом — **PDF-файл**.
5. QR-код в PDF ведёт на страницу проверки подлинности документа.

Пока организаторы не привязали мини-приложение к боту, кнопка открывает то же
приложение в браузере — со входом по подписанной ссылке от бота (метка
«Браузер · вход через бота»). Это настоящий аккаунт MAX, поэтому PDF всё равно
приходит в чат.

### В браузере — без MAX

Открыть https://195-19-202-143.sslip.io → **«Попробовать как студент (демо)»** →
дальше тот же сценарий. Разница одна: браузер вне MAX входит тестовым пользователем
(id 900000–999999), такого аккаунта в MAX нет, и в чат ничего не отправляется —
PDF открывается на экране заявки кнопкой «Открыть PDF». Чтобы увидеть файл в чате,
откройте приложение кнопкой из бота.

### Роль деканата — в один тап

Профиль → **«Включить роль деканата (демо)»** → появится вкладка **«Деканат»**,
в очереди — только ваши заявки. Нетиповая заявка (например, справка об обучении
с включённым «Нужен оригинал с печатью») ждёт сотрудника: Деканат → заявка →
Принять в работу → Передать на подпись → **Выдать документ** → PDF у студента.
Полный сценарий на 13 шагов — [ниже](#демонстрационный-сценарий).

### Возможность MAX: билет на входе — ещё минута

1. Главная → афиша → событие с записью (например, **«Собрание первокурсников ИМИТ»**) →
   **«Записаться»** → **«Мой билет»**: QR и код вида `T12-ABCDE`.
2. Роль деканата (см. выше) → вкладка **«Деканат»** → «Проверка билетов».
3. В мобильном MAX — **«Сканировать QR»**: открывается сканер самого MAX, с одного
   телефона можно выбрать скриншот билета из галереи. В браузере и в web-версии MAX
   сканера нет — код с билета вводится в поле → **«Отметить»**.
4. «✓ Проход отмечен: ФИО, группа — событие»; повторная проверка — «Уже проходил(а)».
   Открытый билет у студента через пару секунд сам меняется на «✓ Проход отмечен».

С ноутбука сканер, вибрацию и окно «Поделиться» MAX показывает встроенный эмулятор
клиента: добавьте к адресу `?maxEmu=android`. Что где работает и чем заменяется —
[Возможности MAX сверх минимума](#возможности-max-сверх-минимума).

### API — пять запросов

Для проверки без MAX сервер принимает тестовый вход `dev:<id>:<Имя>` — только для
id 900000–999999 (настоящим пользователем MAX без подписи не представиться).
Запросы для bash, Git Bash или WSL:

```bash
BASE=https://195-19-202-143.sslip.io
AUTH="Authorization: MaxInitData dev:$((900000 + RANDOM)):Expert"   # свой тестовый id

# 1. Сервис жив — без авторизации
curl -s -w '\n' $BASE/api/health

# 2. Демо-вход: своя копия синтетического студента, код не нужен
curl -s -w '\n' -X POST -H "$AUTH" $BASE/api/binding/demo

# 3. Какие справки можно заказать: формы описаны JSON-шаблонами
curl -s -w '\n' -H "$AUTH" $BASE/api/requests/templates

# 4. Справка об обучении — типовая, выдаётся в том же запросе.
#    purpose = «В банк», записан \u-кодами, чтобы не зависеть от кодировки терминала
DOC=$(curl -s -X POST -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"template_key":"study_certificate","payload":{"purpose":"\u0412 \u0431\u0430\u043d\u043a"}}' \
  $BASE/api/requests | grep -o '"uuid":"[^"]*"' | cut -d'"' -f4)
echo "документ: $DOC"

# 5. Проверка подлинности (то, что открывает QR) и сам PDF — без авторизации
curl -s -w '\n' $BASE/api/verify/$DOC
curl -s -o spravka.pdf $BASE/api/documents/$DOC
```

Что ожидать:

| № | Ответ |
|---|---|
| 1 | `{"status":"ok", … "features":{"bot":true,"assistant":true}}` |
| 2 | Профиль: `"is_bound":true`, `"group_name":"Б-25-1"`, `"record_book_no":"DEMO-…"`, `"is_demo":true` |
| 3 | Девять шаблонов с полями форм; у `study_certificate` — `"auto_issue":true` |
| 4 | `документ: <uuid>` — справка выдана в том же запросе. Без `\| grep …` видна вся заявка: статус `ISSUED`, в истории «Демо-деканат (автоматическая выдача)», в `document` — `download_url` и `verify_url` |
| 5 | `"valid":true` и номер справки; `spravka.pdf` — одностраничный PDF с QR-кодом |

Тот же вход с нетестовым id (`dev:12345678:X`) получает 401. Остальные методы —
в OpenAPI; коды ошибок, роли и лимиты — в [`docs/06-api.md`](docs/06-api.md). Весь
сценарий одной командой — `scripts/check_data_api.py`, см. [«Собственный API»](#собственный-api).

## Как запустить

Одна команда поднимает всё локально — базу и приложение (API + фронтенд):

```bash
git clone <репозиторий> && cd max-campus
cp .env.example .env          # заполнить MAX_BOT_TOKEN, YC_API_KEY, YC_FOLDER_ID
python -c "import secrets; print(secrets.token_urlsafe(32))"   # вывод — в .env: MAX_WEBHOOK_SECRET=<вывод>
docker compose up -d --build  # http://localhost:8000
```

Секрет вебхука нужен и без бота: им же подписаны коды билетов на события. С пустым
`MAX_WEBHOOK_SECRET` вебхук принимает любой запрос, а смоук не засчитывает проверку
«чужой секрет → 403». `MINIAPP_PUBLIC_URL` в примере — `http://localhost:8000`;
на сервере это публичный HTTPS-адрес. Без ключей MAX и Yandex приложение тоже
поднимается: не уходят сообщения в чат и выключен ассистент.

Версии зависимостей зафиксированы: образ ставит Python-пакеты из
`backend/requirements.txt`, фронтенд — `npm ci` по `frontend/package-lock.json`.
Чистая сборка образа (`docker build --no-cache`, базовые образы уже скачаны) — 98 с
при лимите кейса 5 минут; 90 из них pip скачивает пакеты (решение 075).

Корневые сертификаты Минцифры (без них нет TLS до MAX API) уже лежат в `certs/`;
обновить — `bash scripts/fetch_certs.sh`. База наполняется сама при первом старте:
шаблоны заявок, база знаний, студенты, события, конкурсы и объявления. Отдельных
миграций запускать не нужно.

Публичный HTTPS — он нужен MAX для мини-приложения и вебхука:

```bash
# Свой сервер, как на стенде: в .env PUBLIC_HOST=1-2-3-4.sslip.io (IP через дефисы)
docker compose --profile vps up -d --build     # Caddy сам получит сертификат Let's Encrypt

# Без сервера: временный адрес cloudflared, меняется при каждом перезапуске
docker compose --profile tunnel up -d
docker compose logs tunnel | grep trycloudflare
```

Туннель — только для проверки у себя: крупные российские провайдеры режут
Cloudflare, и у части пользователей вместо приложения белый экран (решение 048).
Для экспертов стенд работает на VPS.

**Проверка, что всё поднялось:**

```bash
curl http://localhost:8000/api/health
python scripts/smoke_test.py      # сквозной сценарий, безопасность, демо-вход, билеты: на 28.09 — 96 проверок, все зелёные
DATA_API_TOKEN_STUDENT="MaxInitData dev:990301:Expert" \
  python scripts/check_data_api.py --base-url http://localhost:8000   # DATA-API.yaml: 14 обязательных проверок
bash scripts/reset_demo.sh        # после них: смоук занимает код привязки A7K2-9M, оба выдают справки
python scripts/test_assistant.py  # качество ответов ассистента, 10 сценариев (платные вызовы YandexGPT)
docker compose exec -T app python - < scripts/test_bot_buttons.py   # кнопки бота, без сети
```

### Остановка и повторный запуск

```bash
docker compose stop                 # остановить, всё сохраняется
docker compose up -d                # запустить снова — с теми же данными
docker compose up -d --build app    # после правки кода: пересобрать только приложение
docker compose down                 # удалить контейнеры; данные остаются в томах

bash scripts/reset_demo.sh          # вернуть демо-данные в исходное состояние, не останавливая сервис
```

```bash

```

### Обслуживание сервера

```bash
# на VPS, под root, из /opt/max-campus — один раз после первой выкладки
bash scripts/vps_maintenance.sh          # ночная копия базы и справок + подъём после перезагрузки
bash scripts/vps_maintenance.sh backup   # снять копию сейчас
```

Копии — `/opt/max-campus/backups`, хранятся 7 последних; команды восстановления —
в шапке скрипта. Логи контейнеров ограничены: по 10 МБ, три файла на сервис.
Даты демо-событий и срок демо-объявлений приложение само пересчитывает раз в сутки —
перезапускать его ради этого не нужно (решение 065).

## Демонстрационный сценарий

Основной путь, который проходят эксперты. Кодов не нужно: каждый аккаунт получает
свою копию синтетического студента, а роль деканата включается в один тап — второе
окно не нужно, и эксперты не мешают друг другу. В браузере вне MAX каждому браузеру
выдаётся свой тестовый пользователь.

| Шаг | Что сделать | Что увидеть |
|---|---|---|
| 1 | Открыть приложение → **«Попробовать как студент (демо)»** | Свой демо-профиль: ваше имя из MAX, Б-25-1, 1 курс ИМИТ, зачётка `DEMO-…` |
| 2 | Вкладка **Чат** → «Сколько дней делается справка об обучении?» | Ответ по регламенту со ссылкой на источник |
| 3 | Там же → «Какие справки я могу заказать?» | Список из базы + кнопка перехода к форме |
| 4 | **Заявки → Новая → Справка об обучении** | Форма собрана из JSON-шаблона, не свёрстана руками; пометка «сразу» — справка типовая |
| 5 | Выбрать, куда нужна справка → **«Получить PDF сразу»** | Степпер за пару секунд проходит все шаги: справка выдана автоматически, PDF — в заявке и файлом в чате с ботом |
| 6 | Новая заявка: включить «Нужен оригинал» (или другой вид справки) → отправить | Нетиповая заявка — «Отправлена», ждёт сотрудника, срок в днях |
| 7 | Профиль → **«Включить роль деканата (демо)»** | Появилась вкладка **Деканат**, в очереди — только ваши заявки |
| 8 | Деканат → заявка → Принять в работу → Передать на подпись → **Выдать документ** | PDF сформирован |
| 9 | Вернуться студентом на экран заявки | Документ, кнопка «Открыть PDF» |
| 10 | Открыть QR-ссылку из PDF | Страница проверки подлинности |
| 11 | **Люди** → откликнуться на объявление (✓) | «Демо-отклик»: в «Откликах» пара с меткой «демо» — автор синтетический, его ответ смоделирован; у настоящих студентов там кнопка «Написать» |
| 12 | Главная → событие → **«Записаться»** → **«Мой билет»**; Деканат → «Проверка билетов» → **«Сканировать QR»** (мобильный MAX) или код с билета → «Отметить» | «✓ Проход отмечен» и вибрация на телефоне; билет студента сам меняется на «Проход отмечен», кнопки «Записаться» на карточке больше нет |
| 13 | Событие → **«Поделиться»** | Окно «Поделиться» самого MAX: выбрать чат группы; ссылка открывает приложение сразу на этом событии. На десктопе MAX и в браузере — карточка от бота или системное меню |

Сброс между показами: `bash scripts/reset_demo.sh` — коды привязки снова свободны,
демо-копии и опросы групп (кроме заложенного сидом) удалены.

**Коды для проверки** — второй путь, так входил бы настоящий студент по коду из деканата

|---|---|
| Студент (основной сценарий) | `A7K2-9M` |
| Студенты (запасные) | `B3N8-4P`, `C5R1-7T`, `D9W6-2L` |

## Возможности MAX сверх минимума

Минимум мини-приложения — Bridge, `ready()`, кнопка «Назад» и проверка подписи
запуска. Сверх него Кампус использует возможности самого MAX там, где они дают
пользователю что-то, чего нет у сайта в браузере.

**Проход на событие по QR — камерой MAX.** Студент записывается на событие и
открывает «Мой билет»: на телефоне приложение выводит экран на максимальную яркость
(`requestScreenMaxBrightness`), чтобы код читался с первого раза. Сотрудник на входе
открывает «Деканат → Сканировать QR» — запускается сканер самого MAX
(`openCodeReader`, с выбором снимка из галереи). Сервер проверяет подпись билета
(HMAC, решение 042) и отмечает проход. Результат — сразу на экране и нативной
вибрацией (`HapticFeedback`: успех, «уже проходил», ошибка), а открытый билет у
студента через пару секунд сам меняется на «✓ Проход отмечен» и возвращает яркость.
Проход — конечное состояние: запись после него не отменить, место остаётся занятым.

**«Поделиться» — окном самого MAX.** Кнопка на карточке события открывает
`shareMaxContent`: пользователь выбирает чат группы, одногруппники получают ссылку
`max.ru/t355_hakaton_max_bot?startapp=event_<id>`, которая открывает приложение сразу
на этом событии. Раньше было три шага: бот присылал карточку в личку, её пересылали.

| Функция | Экран | Метод Bridge | Где работает | Если метода нет |
|---|---|---|---|---|
| Сканер билета | Деканат → «Проверка билетов» → «Сканировать QR» | `openCodeReader(true)` | MAX на iOS и Android | Ввод кода с билета: `T12-ABCDE`, `t12 abcde`, ссылка из QR |
| Отклик на результат и нажатия | Проверка билета, кнопки | `HapticFeedback` | MAX на iOS и Android | Вне MAX — `navigator.vibrate`, в web и на десктопе MAX — без вибрации |
| Яркость для QR | «Мой билет» | `requestScreenMaxBrightness` / `restoreScreenBrightness` | MAX на iOS и Android | Без изменений, подпись про яркость не показывается |
| Поделиться в чат | Событие → «Поделиться» | `shareMaxContent({text, link})`, ссылка `startapp=event_<id>` | MAX на iOS, Android и web.max.ru | Десктоп MAX, отказ клиента или ошибка — карточка от бота в личку, её пересылают; тестовый вход в браузере — системное меню или буфер обмена |

Что поддерживает какой клиент — по документации Bridge и коду web.max.ru на 28.09.2026:
веб-версия MAX сразу отвечает `unsupported_method` на сканер, вибрацию и яркость,
а поддержка в десктопном клиенте не описана. Поэтому эти методы вызываются только
при `WebApp.platform` = `ios` или `android`, а «Поделиться» на десктопе сразу идёт
через бота. Решение «мы в MAX» принимается по непустому `initData`, а не по наличию
`window.WebApp`: скрипт Bridge создаёт этот объект и в обычном браузере, но без
транспорта — вызовы там теряются. Код — `frontend/src/shared/max.ts`, решения 071–073.

**Как увидеть с ноутбука.**

- **Браузер, без эмулятора** — функция та же, но без камеры: билет проверяется
  кодом (шаги 12–13 [сценария](#демонстрационный-сценарий)).
- **web.max.ru** (после привязки мини-приложения к боту) — так же кодом, а
  «Поделиться» открывает окно самого MAX: по коду веб-клиента метод там есть,
  вживую до привязки не проверить.
- **Эмулятор клиента MAX** — добавьте к адресу `?maxEmu=android` (или `ios`, `web`,
  `desktop`). Он отвечает на вызовы Bridge так, как ответил бы клиент, в углу —
  метка «Эмулятор MAX · android», справа всплывают вызовы: «вибрация: success»,
  «яркость: максимум», «QR: …». Сканер без параметра спрашивает, что «прочитала
  камера»; `&qr=<код или ссылка>` подставляет ответ сразу. Пример:
  `https://195-19-202-143.sslip.io/?screen=/staff&maxEmu=android&qr=T12-ABCDE` —
  код взять из своего билета. `maxEmu=web` повторяет web.max.ru: кнопки сканера нет.
  Внутри MAX эмулятор не включается, а сервер ему ничего не доверяет — вход тот же
  тестовый.

**Что не проверено.** На настоящем телефоне сканер, вибрация, яркость и окно
«Поделиться» не запускались: без привязки мини-приложения к боту MAX открывает
его ссылкой в браузере, где Bridge не работает. Проверено на эмуляторе с настоящим
скриптом Bridge (`st.max.ru/js/max-web-app.js`) и настоящим сервером; серверная часть
билетов — в `scripts/smoke_test.py`, раздел 16.

## Что внутри

### Заявки и справки — движок, а не набор форм

Тип справки описывается JSON-шаблоном: поля, правила валидации, маршрут
согласования, шаблон документа. Бэкенд по нему проверяет данные, фронтенд —
рисует форму. **Новый вид справки добавляется строкой в таблицу, без единой
правки кода.** Сейчас настроено девять: справка об обучении, в военкомат,
о стипендии, социальная стипендия, материальная помощь, общежитие,
академический отпуск, справка-вызов, обращение в деканат.

Машина состояний: допустимые переходы проверяет движок, а кто их делает — роль
сотрудника. Принимает и передаёт на подпись специалист, «Готова» и выдачу —
только подписант (`STAFF_HEAD`); «Выдана» без PDF через смену статуса невозможна.

```
SUBMITTED → IN_REVIEW → SIGNING → READY → ISSUED
                ↕
           NEEDS_INFO              → REJECTED / CANCELLED
```

Каждый переход пишется в историю и порождает сообщение студенту в чат.
Состояние `NEEDS_INFO` — не украшение: это реальный сценарий «донесите документ»,
и студент отвечает на него прямо из приложения.

**Типовые справки выдаются сразу.** Флаг `auto_issue` в шаблоне: справку
об обучении тот же запрос, что её подал, проводит по тем же шагам машины
состояний, формирует PDF и ставит в очередь сообщения в чат — «заявка принята»
и файл. Выдающий в истории и в PDF — «Демо-деканат (автоматическая выдача)».
Поле с флагом `manual_review` (бумажный оригинал с печатью, особая формулировка)
делает заявку нетиповой — она идёт в очередь сотрудника, как и остальные виды.
Если PDF сформировать не удалось, заявка тоже остаётся сотруднику, а не падает
с ошибкой. Код — `modules/requests/service.py`, решение 059.

### Ассистент — RAG с принудительным заземлением

Устроен не как «поиск по документам», а как рабочий инструмент, которому нельзя
соврать. Четыре механизма, каждый появился после конкретного наблюдаемого сбоя:

1. **Поиск по регламентам выполняется всегда**, до обращения к модели.
   Гибридный: векторный (pgvector) плюс полнотекстовый русский, объединение
   через RRF. Модель не может «забыть» посмотреть документ.
2. **Данные подтягиваются заранее по формулировке вопроса.** На «какие идут
   хакатоны» модель однажды не вызвала инструмент и выдумала три несуществующих
   мероприятия. Теперь факты уже лежат в контексте — выдумывать нечего.
3. **Ответ проверяется после генерации.** Служебные строки вырезаются;
   если инструменты дали данные, а модель всё равно ответила «не знаю»,
   делается ещё один проход с данными в открытом виде.
4. **Ответ не зависает.** Весь ответ укладывается в 25 секунд. Если модель
   не успела или упала, приходит не ошибка, а одна-две выдержки из найденных
   регламентов с пометкой «Модель не ответила — вот что сказано в регламенте».
   На вопрос про свою заявку — не выдержка, а кнопки к заявкам.
   На экране вместо трёх точек — этапы («Ищу в регламентах… → Сверяю с твоими
   данными… → Формулирую ответ…»), через 20 секунд — кнопка «Повторить».
   Повтор не начинает заново, а дожидается того же ответа: второй раз модель
   не спрашивается и вопрос в истории не дублируется.

Инструменты исполняются от имени текущего пользователя — параметра «чей»
в их схеме нет, поэтому «покажи заявки Иванова» не работает by design.
Заявки ассистент не создаёт: он возвращает кнопку, форму заполняет человек.
Исключение — обращение в деканат (крайняя мера, когда ответа нет ни в данных,
ни в регламентах): оно записывается сразу, отдельно от ответа, и не теряется,
даже если модель не договорила.

### Календарь вуза

События с таргетингом по факультету, курсу и группе — первокурсник ИМИТ
не видит собрание аспирантов юрфака. Запись с ограничением мест,
лист ожидания и автоматическое поднятие первого в очереди при освобождении места.
Занятие места идёт в транзакции с блокировкой строки: иначе два одновременных
запроса заняли бы один слот.

Записавшийся получает билет: QR и короткий код `T<номер записи>-<5 символов HMAC>` —
без секрета сервера не подделать, а продиктовать на входе можно. Сотрудник проверяет
билет сканером MAX или вводом кода, проход отмечается один раз (`ATTENDED`), повтор
показывается как «Уже проходил(а)». После прохода запись не отменить, повторное
«Записаться» ничего не меняет, а место остаётся занятым.

### Возможности

Хакатоны, конкурсы, олимпиады, стажировки, гранты. Ранжируются взвешенным
скорингом: совпадение интересов, уместность уровня курсу, близость дедлайна,
сколько однокурсников уже отметились. Никакого машинного обучения — правило
объясняется за пятнадцать секунд и не ломается на пустых данных.

Студенты могут предлагать свои — пока только через API (`POST /api/opportunities`),
формы в интерфейсе нет. Такие публикации уходят на модерацию (тоже через API).
У каждой возможности есть кнопка «ищу команду»: она создаёт объявление
в разделе знакомств. Так два модуля связываются в один сценарий.

### Знакомства для первокурсников

Свайпаются **объявления, а не люди**. Это решает сразу три проблемы: холодный
старт (один человек создаёт несколько карточек), модерацию (проверять нужно текст
объявления, а не человека; сама модерация объявлений ещё не сделана — см.
ограничения) и пустой матч (есть понятный повод написать). Контакт открывается,
когда интерес взаимный.

Плюс поток без свайпов: первокурсник отмечает «хочу наставника», и система сразу
подбирает старшекурсника того же направления, у которого есть свободное место
(квота — два подопечных).

На демо-стенде в колоде только синтетические студенты. Ответить сами они не могут,
поэтому их ответ на отклик смоделирован: пара появляется сразу и помечена «демо»,
контакта нет. Объявления живых аккаунтов на стенде видит только автор — иначе
любой анонимный браузер писал бы в колоду всех экспертов (решение 069).

## Архитектура

```
        MAX-клиент
   ┌──────────┴───────────┐
   │                      │
 Бот                Мини-приложение
 (вход, пуши,       (React + TypeScript)
  доставка PDF)             │
   │                        │ initData в заголовке
   └────────┬───────────────┘
            ▼
    FastAPI (Python)
      ├ проверка подписи запуска
      ├ привязка аккаунта MAX ↔ студент
      ├ движок заявок и машина состояний
      ├ генерация PDF + страница проверки
      ├ ассистент: RAG + вызов инструментов
      ├ календарь, возможности, знакомства
      └ очередь исходящих сообщений
            ▼
   PostgreSQL + pgvector · файлы на диске
```

**Решения, которые стоит отметить:**

- **Один сервис отдаёт и API, и фронтенд.** Одно происхождение, один HTTPS-адрес,
  никакого CORS — для мини-приложения это заметно проще в эксплуатации.
- **Очередь живёт в Postgres**, фоновые задачи — обычные asyncio-циклы.
  Redis и внешний планировщик не заводились сознательно: меньше сервисов,
  меньше мест, где что-то не поднимется на демонстрации.
- **Уведомления идут через таблицу `outbox`** — статусы заявок, PDF, записи
  на события, отклики, опросы — с дедупликацией, ретраями и ограничителем скорости.
  Исключение — ответ бота на команду в диалоге (`/start`, `/help`, нажатие кнопки):
  он уходит сразу из обработчика вебхука, иначе собеседник ждал бы очередь.
  Повторы апдейтов MAX отсекаются словарём в памяти процесса.
- **Тихие часы**: напоминания не уходят ночью, переносятся на утро.

- **Тестовые данные.** Синтетические, в JSON — в `testdata/`, порядок работы с

  удаляет заявки, документы (записи и файлы), диалоги, отклики, демо-копии и тестовые

  Даты событий и срок демо-объявлений сдвигаются от текущего дня сами.
- **Персональные данные.** Справочник студентов синтетический, но данные живых
  людей сервис обрабатывает: у каждого, кто открыл приложение, хранятся id, имя,

  документы вместе с файлами PDF и диалоги; аккаунты MAX (id, имя, username) остаются.
- **Резервные копии.** `scripts/vps_maintenance.sh` ставит на сервере ночную копию
  базы и справок (хранятся 7 последних) — его запускают один раз после первой
  выкладки, см. «Обслуживание сервера».

## Собственный API

Мини-приложение, бот и QR в справке работают через собственные HTTP-методы, поэтому
к решению приложены артефакты для решений с собственным API (кейс, с. 10; FAQ, п. 12):

| Что | Где |
|---|---|
| Адрес API | `https://195-19-202-143.sslip.io` — пути от корня хоста: `/api/…`, `/verify/…` |
| OpenAPI 3.1 | [`openapi.json`](openapi.json) в корне — то же, что сервер отдаёт на `/api/openapi.json`; интерактивно — [/api/docs](https://195-19-202-143.sslip.io/api/docs) |
| Обязательные проверки | [`DATA-API.yaml`](DATA-API.yaml) — формат DATA-API 1.0 организаторов: 14 проверок основного сценария и шаг очистки |
| Тестовые учётные записи | Логинов и паролей нет: тестовый вход `Authorization: MaxInitData dev:<id>:<Имя>`, id 900000–999999 — [`testdata/roles.json`](testdata/roles.json) |
| Тестовые данные | [`testdata/`](testdata) — см. [«Тестовые данные»](#тестовые-данные) |
| Вход, роли, методы, ошибки, лимиты | [`docs/06-api.md`](docs/06-api.md) |

**Сценарий `DATA-API.yaml`:** сервис жив → без авторизации — 401 в едином формате
ошибок → демо-профиль студента → профиль → каталог справок → форма справки об
обучении → заявка (201, справка выдаётся сразу) → заявка с историей и документом →
PDF → проверка подлинности без входа → мои заявки → ответ ассистента с источниками →
роль деканата в один тап → очередь деканата; в конце — очистка (отмена заявки: у
выданной справки — 409, это ожидаемо). Роль `student` — тестовый вход; значение
передаётся проверке отдельно, секретов в файле нет.

**Проверить файл валидатором организаторов**
([gitverse.ru/stasnorman/example-data-api](https://gitverse.ru/stasnorman/example-data-api)).
Валидатор сверяет структуру со схемой, связи проверок (`dependsOn`, `extract`,
path-параметры) и наличие каждого пути и метода в `openapi.json`; запросов он не шлёт.

```bash
git clone https://gitverse.ru/stasnorman/example-data-api.git ../example-data-api
pip install -r ../example-data-api/requirements.txt      # PyYAML и jsonschema
python ../example-data-api/validate_data_api.py DATA-API.yaml \
  --schema ../example-data-api/Example/DATA-API.schema.json
# ПОДТВЕРЖДЕНИЕ файл DATA-API.yaml соответствует версии схемы 1.0
```

**Прогнать сценарий вживую** — `scripts/check_data_api.py` выполняет запросы из
`DATA-API.yaml` так, как это сделает проверка: по порядку, с `dependsOn`, переменными
из `extract`, проверкой кода, типа содержимого, обязательных полей и `bodySchema`
(если установлен `jsonschema`), в конце — очистка. Токен роли — из переменной
`DATA_API_TOKEN_<РОЛЬ>`:

```bash
export DATA_API_TOKEN_STUDENT="MaxInitData dev:990301:Expert"   # любой id 900000–999999
```

Порядок работы:

1. **Загружать ничего не нужно.** Сид кладёт эти данные в пустую базу при первом

## Подключить новый вуз

Код один на все вузы, вуз задают настройки и данные. Коротко:

1. **`.env`** — свой бот и адрес (`MAX_BOT_TOKEN`, `MINIAPP_PUBLIC_URL`, `PUBLIC_HOST`),
   ключ Yandex (`YC_API_KEY`, `YC_FOLDER_ID`), название вуза для PDF
   (`UNIVERSITY_NAME`) и его часовой пояс (`UNIVERSITY_TZ_HOURS`: Москва — 3,
   Новосибирск — 7, Иркутск — 8). Для боевого запуска — `SEED_DEMO_DATA=false`
   (без синтетических студентов, регламентов и событий), `DEMO_MODE=false`,
   `ALLOW_DEV_AUTH=false`.
2. **Виды справок** — JSON-шаблоны в `backend/app/seed/templates.py`: поля, проверки,
   срок, флаг автовыдачи. Обновляются при каждом старте, код движка не меняется.
3. **Регламенты** — строки таблицы `kb_document` (или `seed/knowledge.py`), затем
   `TRUNCATE kb_chunk;` и перезапуск — база знаний переиндексируется сама.
4. **Студенты и сотрудники** — выгрузка контингента в таблицу `student` и коды
   привязки в `binding_code`; сотрудники — список `STAFF` в `seed/demo.py`.

Пошагово, с планом пилота на один институт, метриками и оценкой стоимости
YandexGPT на 1000 студентов — [docs/05-rollout.md](docs/05-rollout.md).

## Известные ограничения

- **Кнопка «Открыть приложение» внутри MAX** (`open_app`) работает после того, как
  организаторы привяжут мини-приложение к боту. До этого бот присылает ссылку в
  браузер с подписанным входом — сценарий «справка в чат» проходится и так.
- **В браузере без MAX** вход тестовый (id 900000–999999): PDF — на экране, в чат
  сообщения не уходят, таких аккаунтов в MAX нет.
- **PDF без электронной подписи** и не заменяет документ с печатью.
- **Ассистент** отвечает целиком, без потоковой печати — до 25 секунд, на экране
  видны этапы. Не больше 20 вопросов за 10 минут на пользователя. Знает только
  15 смоделированных регламентов и данные сервиса.
- **Модерация** возможностей — только через API и только вне демо-стенда; объявлений
  «Людей» модерация не проверяет вовсе (на стенде их видит только автор).
- **Коды на стенде публичные** — это общие синтетические учётки: по коду `A7K2-9M`
  любой войдёт той же студенткой, а кодом `STAFF-001` откроет очередь синтетических
  студентов. Заявок демо-копий экспертов в этой очереди нет.
- **Лимиты живут в памяти процесса**: рестарт их обнуляет. Браузерный вход с
  тестовыми id со многих адресов обходит лимиты на аккаунт и на адрес — это цена
  проверки без регистрации; аккаунты MAX так не размножить.
- **Уведомления тестовым пользователям** не отправляются намеренно.
- **Сканер, вибрация и яркость** работают только в мобильном MAX и только когда
  приложение открыто как мини-приложение, то есть после привязки к боту. На настоящем
  телефоне они ещё не запускались — проверены эмулятором с настоящим скриптом Bridge.
  В web-версии и на десктопе MAX билет проверяется кодом, «Поделиться» на десктопе
  идёт через бота (поддержка окна MAX там не описана).
- **Один сервер** (VPS, 1 ГБ) без резервирования; ночные копии базы лежат на том же
  диске и защищают от ошибки, а не от потери сервера.
- **Один вуз — один часовой пояс**: время вуза — фиксированное смещение от UTC.

## Разработка

```bash
# Бэкенд отдельно (нужна поднятая база: docker compose up -d db)
cd backend && python -m venv .venv
./.venv/Scripts/python -m pip install -r requirements.txt   # те же версии, что в образе
PYTHONPATH=. ./.venv/Scripts/python -m uvicorn app.main:app --reload

# Фронтенд отдельно, с проксированием API на бэкенд
cd frontend && npm ci && npm run dev

# Типы API для фронтенда из живой схемы
cd frontend && npm run api:types
```

Вне мессенджера скрипт Bridge тоже создаёт `window.WebApp`, но с пустым `initData`
и без транспорта: вызовы Bridge там теряются. Приложение распознаёт это по пустому
`initData` (`isInsideMax()` в `shared/max.ts`) и переходит в режим разработки:
вместо подписи отправляется `dev:<id>:<Name>`. Сервер
принимает такой вход только для тестовых id 900000–999999 (`TEST_USER_ID_MIN/MAX`
в `core/config.py`), остальные получают 401. Переключение тестового пользователя —
в профиле. Совсем выключается режим переменной `ALLOW_DEV_AUTH=false`.
Если приложение открыто кнопкой-ссылкой из бота (`?lt=…`), вместо dev-входа идёт
подписанный вход настоящего пользователя MAX — заголовок `Authorization: MaxLink <токен>`,
метка в углу — «Браузер · вход через бота».

### Особенности окружения

- **Кириллица в теле запроса из bash на Windows повреждается.** При ручной
  отладке API payload передавать файлом: `curl --data-binary @file.json`.
  Кода это не касается — Python-клиенты кодируют корректно.
- **Порт 5432 может быть занят** локально установленным PostgreSQL, поэтому
  контейнер поднимается на 5433.
- **TLS до `platform-api2.max.ru`** не работает без корневых сертификатов
  Минцифры: `bash scripts/fetch_certs.sh`.

## Безопасность

- Подпись запуска проверяется на сервере, сравнение constant-time, срок жизни — час
  (рекомендация MAX Bridge). Протухшая подпись — экран «Сессия устарела», а не сырая ошибка.
- Вход без подписи (режим разработки) — только для тестовых id 900000–999999:
  представиться настоящим пользователем MAX нельзя.
- Пока мини-приложение не привязано к боту, кнопка в чате — ссылка в браузер
  с подписанным входом `?lt=<id>.<срок>.<HMAC>` (сутки, секрет `LINK_SECRET` или
  производный от токена бота). Сервер проверяет подпись constant-time и срок,
  фронтенд сразу убирает токен из адресной строки, журнал доступа его вырезает.
  В карточки для пересылки (поделиться событием) токен не кладётся.
  Подделанная и просроченная ссылки — 401, это проверяет `smoke_test.py`.
- Вебхук бота с неверным `X-Max-Bot-Api-Secret` отклоняется (403); без заголовка —
  по флагу `MAX_WEBHOOK_REQUIRE_SECRET`. Работает, когда секрет задан: пустой
  `MAX_WEBHOOK_SECRET` выключает проверку.
- Размер запроса — не больше 1 МБ, вложение к заявке — 10 МБ: тело сверх лимита
  не читается, ответ 413. Вложения — квота на студента и на весь сервер.
- Фронтенд отдаётся только из папки сборки: обход вида `/..%2F..%2Fetc%2Fpasswd`
  получает `index.html`. Это и два пункта выше проверяет `smoke_test.py`.
- Роль сотрудника читается из справочника, а не из запроса, и проверяется по
  действию: выдаёт только подписант, события публикует организатор, модерирует
  модератор. На демо-стенде коды сотрудников общие, поэтому публиковать для всех
  там нельзя, а в очереди по коду нет заявок демо-копий (решение 068).
- Ссылки в публикациях и обложках — только `http(s)`; фронтенд тоже открывает
  только веб-ссылки.
- Готовый PDF и страница проверки открываются по ссылке с uuid4 документа
  (122 случайных бита) без входа — так работает QR-код. Перебрать такие ссылки нельзя,
  а списка документов без авторизации нет.
- База и приложение слушают только `127.0.0.1` хоста; наружу открыты 80 и 443
  (Caddy) и 22 для входа по ключу — остальное закрыто файрволом сервера.
- Подбор кода привязки: 5 попыток в час на аккаунт и 20 неудачных в час с одного
  адреса.
- Демо-вход: аккаунт MAX (подпись запуска или ссылка бота) — без лимита, копия одна
  на аккаунт; тестовые id браузера — 120 копий в час на сервер и 10 с адреса.
  Скрипт больше не может закрыть демо-вход экспертам из MAX (решение 067).
- Инструменты ассистента не принимают идентификатор пользователя параметром.
- Билет на событие — код с HMAC-подписью из 5 символов, чтобы его можно было
  продиктовать. Перебор подписи упирается в лимит: 20 неверных кодов за 10 минут
  на сотрудника (429).
- Вопросов ассистенту — не больше 20 за 10 минут на пользователя, для тестового
  входа — ещё 40 за 10 минут с адреса; голосовой вопрос — так же (429 с понятным
  текстом). Это сдерживает скрипт, но не общий потолок расходов: его задаёт квота
  каталога в Yandex Cloud.
